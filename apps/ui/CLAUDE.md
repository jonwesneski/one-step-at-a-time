# apps/ui — Project Context

## Overview

`@one-step-at-a-time/ui` is a **CRUD-like app for creating and managing sheet
music** (general audience — composers, anyone writing notation). It renders
notation with `@one-step-at-a-time/web-components` and wraps it in an editor.

Stack:

- **Vite** + **TanStack Start** (`spa.enabled: true`) + **TanStack Router**
  (file-based routing)
- **React 19**, **react-hook-form** (the composition-editor store), **Tailwind v4**
- Deployed as a **static SPA** — `vite build` → `dist/client` → nginx
  (`Dockerfile`, `nginx.conf`). No server runs in production. The `start` nx
  target exists but isn't part of the deploy.

## Status & stability

**Early development. Refactors are expected and welcome** — including moving files,
renaming, reshaping the data model, and reworking the patterns described here. If a
change makes the codebase cleaner, do it; don't preserve a shape just because this
doc or existing code describes it. Update this doc when you change a pattern it
documents.

**Only "Create" exists.** The composition form under `/` is the whole app today.

- **Read / Update / Delete** of saved compositions: intended, **not yet designed**.
- **Persistence / backend / API**: none. Nothing is saved anywhere. The form
  builds an in-memory structure and that's it — there's no submit handler yet.

Don't infer a storage model, API shape, or R/U/D screen design from anything here —
those decisions haven't been made.

## The composition form (`app/components/compositionForm/`)

This is the framework to learn and follow. `/` → `index.tsx` → `<ClientOnly>` →
`CompositionInput`.

### Data model — one normalized, undoable structure

The composition lives in a **react-hook-form store** (`useForm` in
`CompositionInput.tsx`). The editable part is a flat, normalized
`CompositionStructure` (`types.ts`): `*Order` arrays for sequence, `*ById` maps for
nodes, every id a `crypto.randomUUID()`.

```
timeSig: TimeSignature                     entriesById:    Record<id, MusicEntry>       (note | chord | rest | clef | barline | guitar-note)
measureOrder: string[]                     connectorsById: Record<id, NormalizedConnector> (tie | slur | hairpin | glissando | hammer-on | pull-off | slide, by entry id)
measuresById: Record<id, { staffIds, time?, repeatStart?, barline?, ending?, endingLabel? }>   connectorOrder: string[]
stavesById:   Record<id, NormalizedStaff>  tupletsById: Record<id, { ratio, placement, crossStaffGroupId }>
              (type: treble | bass | vocal | guitar-tab; label, part; vocal: voiceType, lyrics; tab: tabFor)
                                           octaveSpansById: Record<id, NormalizedOctaveSpan> (8va/15ma… lines, by entry id)
                                           tremolosById:   Record<id, NormalizedTremolo>  (two-note tremolos; members carry tremoloId)
                                           arpeggiosById:  Record<id, NormalizedArpeggio> (written-out arpeggios; run notes carry arpeggioId)
```

`NormalizedStaff` is a union discriminated by `type`. Staff **settings** (type,
group, label, part, voice type, tab link) are copied onto new measures by
`staffSettingsHelpers.ts#staffSettingsOf`; a vocal staff's `lyrics` are one
measure's text and stay with it. `label` and `part` are set track-wide (the
same staff index in every measure, `staffTrackIds`), since the library only
draws a label at each row start and matches `tab-for` per measure.

**Cross-entry notation links** mirror the library's own attribute shapes rather
than inventing collections: N:M shared keys live on the entries
(`beamGroupId` → `beam-group`, `slurGroupId` → `slur-group`, like `tupletId`),
a 1:1 link points at the partner entry (`sharedStemWithEntryId` →
`shared-stem-for`, written on the lower staff's entry, which is why every
entry renders `id={entry.id}`), and a span with metadata gets its own
collection (`octaveSpansById`, like connectors). The library warns about and
drops an invalid link, so the editor never stores one:
`notationLinksHelpers.ts#pruneInvalidNotationLinks` runs every per-feature
`pruneInvalid*` pass and is called last by every mutation that can move,
delete, or re-time entries (`applyEntryUpdate`, `removeSelectionFromStructure`,
`moveEntryInVoice`/`moveEntryToVoice`, `removeVoiceFromStaff`, `rebar`, the
`setTuplet` mutator), followed only by `pruneBrokenTies` where ties are
re-checked, since tie validity reads octave spans. A new link type adds its
own `pruneInvalid*` to that list.

**Octave spans store written pitch.** Applying one keeps its members sounding
where they were, so written octaves move opposite to the shift (8va: one
down); removing it or changing the amount moves them back
(`octaveHelpers.ts`). Deleting an endpoint shrinks the span to the notes left
(`octaveSpansWithoutEntries`, computed on the structure _before_ the delete)
rather than re-pitching anything. A reordered entry joins the span it lands
in and is re-pitched to keep its sound (`octaveSpansAfterMove`); ties compare
sounding pitch (`soundingOctaveShift`), so a tie may cross a line's edge.

A staff's entries are one level deeper than the diagram above shows:
`voiceOrder: string[]` (ascending = voice 1..3, position IS the voice number,
mirrors the library's `<music-voice>` model) + `voicesById: Record<id, {
id, entryIds }>`. A staff's "Voices" tab (`VoiceInput.tsx`, mounted from
`StaffInput.tsx` alongside "Staff Entries") adds/removes a voice
(`addVoice`/`removeVoice` mutators, wrapping `voiceHelpers.ts`'s
`addVoiceToStaff`/`removeVoiceFromStaff`, capped at 3 like the library); the
"Staff Entries" add-panel gets a Voice selector once a staff has 2+ (hidden
for the common single-voice case); an existing entry can be relocated to a
different voice via a "Voice" selector in its own Edit panel
(`moveEntryToVoice` mutator) — real drag-to-another-voice is not implemented
(today's reorder-drag is single-voice by construction; moving voices is a
plain control, not drag). A `ClefEntry` always lives in `voiceOrder[0]`'s own
`entryIds` — a clef change is staff-wide, but the library only honors a
mid-stream `<music-clef>` nested in the first `<music-voice>` — so the
add-panel's Voice selector never appears on the Clef Change tab. Use
`voiceHelpers.ts`'s `staffEntryIds(staff)` for anything that genuinely needs
"every entry in this staff regardless of voice" (deletion cascades,
staff-wide search, marquee hit-testing) rather
than reading `voicesById` directly.

`keySig` / `mode` inheritance is **not** stored per node — it lives on the root
form values, passed straight to `<music-composition>`, and the library flows it
down. **Time signature is different: it's positional** — see piece 9.

Editing an existing entry goes through `updateEntry` → `applyEntryUpdate`
(`entryEditsHelpers.ts`, in-place replace by id). `EntryEditInput` is its panel.

### The pieces — patterns to follow for new features

**1. Structural mutations go through `record()`.** Every change to
`CompositionStructure` is a pure "build the next structure" step followed by
`record(next)` (`useUndoRedo`). `record` snapshots the current structure into the
undo stack, then writes the new one. Never call `methods.setValue` on a structural
field directly — you'd skip undo history.

- Mutators (`addMeasure`, `addStaff`, `setStaffGroup`, `addVoice`, `removeVoice`,
  `moveEntryToVoice`, `addEntry`, `setConnector`, …) are defined in
  `CompositionInput.tsx`, passed into `CompositionFormSessionProvider` as `on*`
  props, and re-exposed through `useCompositionFormSession()`. A mutator that is
  just one pure structure-in/structure-out helper doesn't need that threading:
  call `editStructure((s) => helper(s, …))` from the panel — it records one undo
  step, and nothing when the helper returns its input unchanged (the Octave,
  Cross-staff Beam, Shared Stem, Phrase Slur and cross-staff Tuplet panels all
  work this way). A mutator whose effect can invalidate the current selection
  (deletes/moves ids the selection references) gets a small wrapper defined
  _inside_ the provider instead of a raw pass-through — see `removeVoice`
  (drops now-dangling entry ids from `session.selection` after the delete) and
  `confirmTimeSignatureChange` (clears the selection outright after a rebar
  mints fresh ids).
- `getStructure` / `setStructure` in `CompositionInput.tsx` bridge the form store
  and `useUndoRedo`. If you add a field to `CompositionStructure`, add it in **four
  places**: the type, `defaultValues`, `getStructure`, `setStructure`.

**2. `useUndoRedo<T>(getValue, setValue)`** (`hooks/useUndoRedo.ts`) — generic
snapshot stacks (`past` / `future`). Cmd/Ctrl+Z, Cmd+Shift+Z / Ctrl+Y are bound in
`CompositionFormBody`. It's structure-agnostic; you don't touch it to add a
feature, as long as the feature's state is inside the `CompositionStructure` slice
it snapshots.

**3. `CompositionFormSessionContext`** holds state that is **not** part of the
submitted composition and **not** undoable: the current `selection`, which
`DockedTabPanel` tab is open, the last-used entry type. Shallow-merged via
`setSession(patch)`. It also owns the DOM ref maps (measure/staff/entry elements)
used for hit-testing, and forwards the mutators from `CompositionInput`. Put
transient editor UI state here; put anything that should survive undo/redo or a
future save in `CompositionStructure`.

**4. Selection** (`Selection = { measureIds, staffIds, entryIds }`, in `types.ts`;
`EMPTY_SELECTION` / `isSelectionEmpty` helpers):

- **Plain click** on a measure/staff/entry → replaces the selection with just that
  node (`selectMeasure` / `selectStaff` / `selectEntry`).
- **Shift / Cmd / Ctrl + click an entry** → toggles it in `selection.entryIds`
  (added for tie/slur, which need 2+ entries).
- **Drag-marquee** (`SelectionCanvas` wraps `<music-composition>` in a padded
  canvas that fills the rest of the viewport, so a drag can start outside any
  measure) → `computeBoxSelection` (`selectionHelpers.ts`, pure + unit-tested)
  turns a `DOMRect` into a `Selection`, promoting to measure/staff level when the
  box covers ≥ `COVERAGE_THRESHOLD` of the element. The gesture lives in
  `useMarqueeSelection`, with its pure math in `marqueeHelpers.ts`:
  - Mouse defers pointer-capture until it crosses `DRAG_THRESHOLD_PX` so plain
    clicks still bubble; touch needs a `LONG_PRESS_MS` hold so swipes still scroll.
  - The anchor is stored in **page** coordinates and the page auto-scrolls near
    the viewport's top/bottom edge, so a box can span more than one screen.
  - **Shift / Cmd / Ctrl + drag** merges into the current selection
    (`mergeSelections`); a plain drag replaces it.
  - A pointerdown on a form control or inside `[data-marquee-ignore]` (the
    `DockedTabPanel`) never arms a marquee.
- Marquee results come out in **document order** (a modifier-drag appends its new
  ids in document order after the existing ones); shift-click results in click
  order — sort by document position when order matters.
- **Click on empty canvas** (the canvas itself, or a gap inside
  `<music-composition>`, which shadow-DOM retargeting reports as the host) →
  `clearSelection`.
- What a selection _enables_ is up to each component: `MeasureInput` shows an "Add
  Staff" / "Group Staves" / "Ties & Slurs" tab for measure / multi-staff / entry
  selections; `Backspace`/`Delete` deletes any non-empty selection.
- **Note drag coexists with the marquee** (piece 10): a pointerdown that lands on a
  note/chord/rest is claimed by `useEntryDrag` (`e.stopPropagation()` before
  `SelectionCanvas`'s bubble-phase handler sees it), so the marquee only ever
  starts from whitespace. Same deferred-capture + threshold +
  post-drag click-swallow as the marquee, so a plain click still selects.

**5. `DockedTabPanel` — every entry/structure editor lives here.** Any control
that edits a measure, staff, entry, or connector renders as a **tab in this panel**,
never as an inline panel elsewhere. The exceptions are the root form fields
(`BasicInfoInput`), the Undo/Redo/Delete toolbar, and `MeterChangeDialog` (a
modal, not a tab — see piece 9) — none are selection-contextual. It's docked
full-width to the bottom of the window on every screen size (a fixed 25vh on
mobile; up to 40vh on desktop, sized to its content), with a sideways-scrolling
tab row and a vertically scrolling body. Its tabs are just an array of
`{ label, content }`; callers build the array conditionally and pass it, and the
active tab is remembered by label in `session.entryPanelTab`.

- **Selection-scoped** editors mount their tab from `MeasureInput` (measure- or
  entry-scoped) or `StaffInput` (staff-scoped). `CompositionFormBody` pads the
  page bottom by the dock's height whenever the selection is non-empty, so the
  last row of the score can scroll above it.
- Each mounting component renders its own panel instance, all in the same docked
  spot — when several are open at once (e.g. two selected staves each show their
  own Note/Chord/… panel alongside the measure's), they stack and only the last
  is visible.
- An editor that **spans measures** (e.g. `ConnectorInput` for a cross-barline tie)
  mounts from the `MeasureInput` that holds the selection's **start** node, so
  exactly one panel shows.

**6. Rendering to web-components.** JSX renders the custom elements directly
(`<music-composition>` → `<music-measure>` → `<music-staff>` →
`<music-note>`/`<music-chord>`/`<music-rest>`). No wrapper components. The JSX prop
contract is declared in `packages/web-components/src/react.d.ts` (published as the
`@one-step-at-a-time/web-components/react` subpath). Conventions:

- pass `value ?? undefined` so a cleared value removes the attribute;
- to derive per-element props from the **whole** structure (not just one node),
  add a hook like `useConnectorAttributes()` (`useCompositionStructure.ts`) —
  `useWatch` the slices, `useMemo` a pure resolver, read it in `StaffInput`;
- `MeasureInput` / `StaffInput` register each element in the session ref maps via
  callback ref for hit-testing.

**7. Pure logic, optionally with a light colocated test.** Non-trivial transforms live in a plain
`.ts` that can sit next to a `.test.ts` (vitest, no React; see the light-testing rule
under Build & test): `deleteSelectionHelpers.ts`,
`selectionHelpers.ts`, `staffGroupsHelpers.ts`, `connectorsHelpers.ts`. Keep them
`this`-free and structure-in/structure-out so they're trivially testable — the
components stay thin. When such a helper mirrors a rule that also lives in
`packages/web-components` (e.g. `staffGroupsHelpers.ts` ↔ the library's brace/bracket
pairing, `connectorsHelpers.ts` ↔ `pairConnectors`, `clefsHelpers.ts` ↔ `staffClassicalBase.ts`
clef-segment + octave resolution), say so in a header comment and note that this
app only has to handle well-formed data since it's the sole writer.

**8. Cascade cleanup on delete.** `removeSelectionFromStructure`
(`deleteSelectionHelpers.ts`) computes the ids to remove, then rebuilds every collection
without them **and** repairs anything left dangling — a group that dropped below 2
staves, a connector whose endpoint is gone — finishing with
`pruneInvalidNotationLinks`. Any new collection that references node ids needs its
own filter here (or a `pruneInvalid*` pass in `notationLinksHelpers.ts`).

**9. Time signature is positional; measure capacity is enforced.**

- **Positional meter.** `structure.timeSig` is the measure-1 meter;
  `NormalizedMeasure.time` is a **sparse** override that holds until the next one.
  `timeSignaturesHelpers.ts` resolves it (`effectiveMeters`, `meterAt`, `meterOfEntry`,
  `meterRegionAt` — a _meter region_ is a run of measures under one meter). The app
  is the authoritative writer: `MeasureInput` writes the resolved `time` onto
  **every** `<music-measure>` (via `useMeasureMeters()`), so the library never has
  to infer it. Measure 1 never carries an override (`MeasureMeterInput` routes it
  to the composition meter).
- **Capacity.** `measureCapacityHelpers.ts` mirrors the library's
  `measureRules.computeAllowedElementCount` (tuplet-aware). The renderer silently
  drops entries past a measure's budget, so overfill must be prevented: the
  duration dropdowns filter to `fittingDurations(...)`, and `applyEntryUpdate`
  clamps as a backstop. `MeasureInput` shows a red overfull indicator when a staff
  still exceeds its meter (post-rebar edge cases, or a "signature only" change).
- **Meter changes go through a dialog.** The Time control (`BasicInfoInput`) and
  the per-measure "Time Signature" tab (`MeasureMeterInput`) set
  `session.pendingMeterChange`; `MeterChangeDialog` (rendered by
  `CompositionFormBody`) offers **Rewrite** vs **Signature only** vs Cancel.
  `confirmMeterChange(rewrite)` calls `setCompositionMeter` / `setMeasureMeter`
  (`rewrite: boolean`) — one `record()` per change.
- **Rebar** (`rebarHelpers.ts`) is the reflow for `rewrite: true`: per staff index, it
  concatenates the region's entry stream and re-slices it to the new capacity,
  splitting barline-crossing notes into the fewest durations (`durationHelpers.ts`
  `decomposeToDurations` — a single dotted value where one fits, else a **tie
  chain**), moving tuplet runs, tremolos and written-out arpeggios
  whole (`entryWrappersHelpers.ts#resolveAtomicRuns`), minting/dropping
  measures, and re-anchoring ties. The region's final
  measure may be left under-full (no rest padding). Because it mints new
  measure/staff ids, the mutator clears the selection afterward.
- **Rebar and repeats/lyrics.** Rebar keeps the region's first-bar
  `repeatStart` and last-bar `barline`. Repeat or ending marks anywhere else in
  the region would be lost, so `rebar` refuses (`REBAR_REPEATS_REASON`) and the
  dialog disables Rewrite. A vocal staff's lyrics can't be re-sliced by beat:
  rewritten bars' verses are joined onto the region's first bar (the dialog
  says so).

**10. Note drag — pitch + reorder — is the app's, not the library's.** The
web-components library renders notation and reports pointer/click events; it has
no `editable` staff. `useEntryDrag` (`useEntryDrag.ts`) is the pointer state
machine, wired onto every note/chord/rest via `onPointerDown` in `StaffInput`.

- **Hit-test** `e.nativeEvent.composedPath()` (`entryDragHelpers.ts`
  `isNoteheadPath`): a notehead (`.head` / `.head-hit-zone`, rendered
  unconditionally by the library) → vertical **pitch** drag; anything else on a
  multi-entry staff → horizontal **reorder** drag.
- **Pitch** snaps by diatonic step: `pitchAfterVerticalDrag` divides the pointer
  Δy by `STAFF_Y_STEP` (5px, mirrored from the library's `notationDimensions.ts`;
  the staff lays vertical positions out in raw CSS px), clamps to the clef range
  from `clefsHelpers.ts`, and skips a chord's other notes. Live preview writes the
  `note`/`octave` attribute straight onto the light-DOM element, and the library
  re-renders it in place. Commit reuses `updateEntry`.
- **Reorder** computes a drop index by geometry over the entry's own voice's
  `entryElements` rects (`reorderTargetIndex`), then `reorderEntry` →
  `moveEntryInVoice` (`reorderHelpers.ts`), which splices that voice's
  `entryIds` and repairs the fallout:
  dissolves a tuplet whose run is no longer contiguous, swaps inverted connector
  endpoints, prunes now-invalid ties.
- Overlays (drop clone, drop indicator, `D4 → F4` tooltip) are appended to
  `document.body` at `z-index: 60`. `entryElements` / `staffElements` (the id →
  DOM maps) are exposed on the session context for this and the marquee.

**11. A staff's voices are edited through selectors, not drag.** The data
shape (`voiceOrder`/`voicesById`), the `addVoice`/`removeVoice`/
`moveEntryToVoice` mutators, and the `ClefEntry`-always-in-`voiceOrder[0]`
rule are covered in Data model above — see piece 1 for the `removeVoice`
selection-cleanup wrapper.

- `VoiceInput.tsx` (the "Voices" tab, mounted from `StaffInput`) is the only
  place a voice is created or removed. It's a plain list + Add/Remove
  buttons, not a drag surface.
- `moveEntryToVoice` is exposed as a "Move to Voice" `<Select>` in the
  entry's own Edit panel (`EntryEditInput`), not as a drag target. **This is
  deliberate, not a placeholder**: `useEntryDrag` (piece 10) has no
  cross-voice awareness at all — its reorder path computes a drop index
  against the dragged entry's _own_ voice's `entryElements` rects only, with
  no other-voice hit-testing or Y-axis/row disambiguation to extend. Building
  real drag-to-another-voice would need that disambiguation heuristic from
  scratch; a selector ships the capability now without it. Revisit only if
  real usage shows the selector too slow for dense multi-voice editing.

**12. Notation beyond the basics — what's where.**

- **Entry markings** (`markingsHelpers.ts`): noteheads (note, chord, per chord
  tone, per grace note), single-note tremolo (+ numeral, label, articulation
  repeat), trills (line, end notch, trilling note/accidental, closing notes),
  the arpeggio sign (+ hairpin, `sempre arpeggiando`), dynamic/accidental
  reminders and laissez-vibrer ties are flat fields on `EntryMarkings`,
  serialised by `serializeMarkings` / `serializeLaissezVibrer` /
  `serializeChordTone`. `sanitizeMarkings` clears whatever another edit made
  meaningless (e.g. strokes a shorter value can't carry, a triangle head in a
  chord); `sanitizeEntryMarkings` runs in `pruneInvalidNotationLinks`. Panels:
  the Notehead, Tremolo, Trill and Arpeggio tabs on a single selected entry.
- **Links**: cross-staff arpeggio `arpeggioWithEntryId` → `arpeggio-for`
  (`crossStaffArpeggioHelpers.ts`, modelled on shared stems).
- **Connectors**: glissando is its own connector family (`connectorFamily`),
  so it sits alongside a slur. A tie's `style` and a glissando's `hint` live
  on the connector and are written on the start entry. Laissez-vibrer uses
  the element's single `tie` attribute, so it is never on a tie endpoint
  (`pruneLaissezVibrerOnTies`; a note rebar splits loses it).
- **Repeats** (`repeatsHelpers.ts`, Repeats tab on a measure, root
  `doubleBarBeforeRepeat` / `endingNumbering`): measure fields map to
  `repeat-start` / `barline` / `ending` / `ending-label`. The tab shows the
  library's own warnings by running its exported `resolveEndings`,
  `resolveRepeatSpans` and `repeatPickupWarning` over the same events
  `<music-composition>` builds. A mid-bar `<music-barline>` is a `BarlineEntry`
  — like a `ClefEntry`: zero duration, voice 1 only (`isMarkerEntry`).
- **Wrappers** (`tremolosHelpers.ts`, `arpeggiosHelpers.ts`,
  `entryWrappersHelpers.ts`): members carry `tremoloId` / `arpeggioId`
  (an arpeggio's target is `NormalizedArpeggio.targetEntryId`); `StaffInput`
  nests `<music-tremolo>` / `<music-arpeggio>` inside tuplet runs.
  `measureCapacityHelpers.ts#entryFactor` takes the structure: a tremolo
  member counts 1/N, an arpeggio run note 0, mirroring the library's
  `durationContribution`. Both have prune passes in
  `pruneInvalidNotationLinks`.
- **Vocal staff** (`lyricsHelpers.ts`, `LyricsInput.tsx`): the clef range
  follows the voice type (`clefsHelpers.ts#staffRangeKey`, incl. mezzo, alto
  and tenor on treble-8vb); no clef changes.
- **Guitar tab** (`GuitarNoteInput.tsx`): `GuitarNoteEntry` lives only on a
  `guitar-tab` staff, which renders its notes directly (no voices, rests,
  tuplets or markers). `isTimedEntry` covers anything with a duration
  (`PitchedEntry` stays notation-only). Techniques are connectors;
  `tab-for` links are validated by `staffSettingsHelpers.ts#tabLinkProblem`.
  The library marks tab as incomplete, so this is provisional.

### Component tree

```
CompositionInput                       owns useForm + useUndoRedo + all mutators
└─ CompositionFormSessionProvider       selection, panel state, ref maps, mutator forwarding
   └─ FormProvider (react-hook-form)
      └─ CompositionFormBody            watches root values; Undo/Redo/Delete bar; MeterChangeDialog; renders:
         └─ SelectionCanvas             score canvas: marquee selection (useMarqueeSelection), click-empty-to-clear
            └─ <music-composition>
               ├─ MeasureInput ×N  → <music-measure time=meter repeat-start barline ending ending-label>   (+ Measure / Repeats / Group Staves / Connections / Edit / Grace / Notehead / Tremolo / Trill / Arpeggio / Octave / Tuplet / Tremolo Group / Written-out Arpeggio / Cross-staff Beam / Cross-staff Tremolo / Cross-staff Arpeggio / Shared Stem / Phrase Slur panels)
```

## Adding a feature to the Create form

Use as a menu, not a mandatory sequence.

1. **Structural or session state?** Does it change the composition (undoable, would
   be saved) or is it transient editor UI? → `CompositionStructure` slice vs
   `CompositionFormSession`.
2. **Types** → `types.ts`. A new top-level collection → add `xById` + `xOrder`
   (a collection owned by a parent node is ordered by the parent's id array
   instead, like `entryIds`); wire the four spots in `CompositionInput.tsx`
   (type, `defaultValues`, `getStructure`, `setStructure`).
3. **Pure logic** → `<feature>.ts` (mirror `staffGroupsHelpers.ts`), plus at most
   a happy-path test or two in `<feature>.test.ts`.
4. **Mutator** → a function in `CompositionInput.tsx` that builds the next
   structure and calls `record(next)`; thread it through the provider `on*` prop
   and the context value.
5. **UI panel** → `<Feature>Input.tsx`, always as an `DockedTabPanel` tab (never
   inline). Selection-scoped → a tab from `MeasureInput`/`StaffInput`. Spans
   measures → a tab from the `MeasureInput` holding the selection's start node.
6. **Selection** → decide what selection makes it available; extend `selectEntry`
   or `computeBoxSelection` only if you need a new selection behaviour.
7. **Render** → pass new attributes/children to the `<music-*>` elements; add a
   derive hook if the props depend on the whole structure.
8. **Cleanup** → filter in `removeSelectionFromStructure`.
9. `npx nx format:write && npx nx test ui && npx nx typecheck ui && npx nx lint ui`.

## Design system (`app/design-system/`)

`Button`, `Radio`, `Select`, `TextInput` — thin Tailwind-styled wrappers over the
native elements, re-exported from `design-system/index.ts`. **Stays in `apps/ui`**;
not a separate package. Use these instead of raw `<button>`/`<select>` in form UI.
(The README's "design system" phrasing predates this; the notation renderer is
`@one-step-at-a-time/web-components`, a separate concern.)

`.rainbow-selected` (`globals.css`) is the animated selection outline — add the
class to a selected element.

## Conventions

- Curly braces on every `if`/`else` branch — see the root `CLAUDE.md`.
- Comments: default to none; see the root `CLAUDE.md` comment rules. Design-decision
  rationale is welcome (e.g. `useMarqueeSelection`'s pointer-capture-deferral note).
- Form sub-components are named `<Thing>Input.tsx`.
- react-hook-form is the model store. Components subscribe with `useWatch({
control, name })` or `useFormContext().watch(name)` — both are in use; pick
  whichever reads cleanest for the component.
- Functional components only; hooks in `app/hooks/` when reused.
- `routeTree.gen.ts` is generated — never hand-edit; it regenerates on `vite dev`.

## Build & test

Run from the monorepo root via nx (never the underlying tool directly):

| Task       | Command               | Notes                                         |
| ---------- | --------------------- | --------------------------------------------- |
| Dev server | `npx nx dev ui`       | `vite dev`                                    |
| Build      | `npx nx build ui`     | static SPA → `dist/client`                    |
| Unit tests | `npx nx test ui`      | `vitest run`, jsdom, `app/**/*.test.{ts,tsx}` |
| Typecheck  | `npx nx typecheck ui` | `tsc --noEmit`; builds web-components first   |
| Lint       | `npx nx lint ui`      |                                               |
| Format     | `npx nx format:write` | run after every batch of edits                |

**Keep unit tests very light.** The UI's look and behaviour are still being worked
out, so code here gets reshaped or deleted often, and every test is one more thing
to update. Write at most one or two happy-path tests per helper. Write zero (or at
most one happy-path test) for component and hook files. Don't add edge-case
matrices or exhaustive coverage. When a change makes an existing test obsolete,
delete the test rather than preserving it.

**Testing today is pure-function unit tests only** — vitest + jsdom, local fixture
builders returning `CompositionStructure` (or a `Pick<>` of it), asserting on the
returned object. No React Testing Library, no component/hook tests, no Storybook in
this app. Follow that style for new logic; if you need to test a component,
introducing RTL is a reasonable call — flag it.

### Gotchas

- **Web components need the browser.** `customElements.define()` and Shadow DOM
  don't exist server-side, and a tag can't be registered twice. Anything importing
  `@one-step-at-a-time/web-components` must render under `<ClientOnly>`. HMR on a
  web-components source edit silently no-ops — **hard-refresh** to see it (see the
  root `README.md`).
- **Dev resolves the library from source** via the `one-step-at-a-time` export
  condition (`vite.config.ts`), so web-components edits are picked up without a
  rebuild — but `typecheck` depends on the web-components **build**, so run
  `npx nx build @one-step-at-a-time/web-components` after changing its public
  types.
- `crypto.randomUUID()` is used for all node ids — fine in the browser and in
  jsdom/vitest.
